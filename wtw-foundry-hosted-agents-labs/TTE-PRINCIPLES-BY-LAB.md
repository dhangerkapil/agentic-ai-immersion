# Technical features by lab, mapped to Turing Team Engineering

This file takes the "Technical features taught, by lab" table from `README.md` and adds a column:
which Turing Team Engineering (TTE) principles, methods and techniques apply to each lab, and how.

Source for the framework: the `turingteamengineering` repository (`principles.md`,
`analysis/principle-category-map.md`, `INSIGHTS.MD`, `REPO-INDEX.md`). Test ids (t01-t23) are the SWE
A/B suite on Copilot CLI; a01-a12 are the Azure agent-operations suite on a support-triage agent with
`gpt-5.4-mini`. Verdicts are quoted as the framework states them, including the conditional and
negative ones, because the framework's own rule is that the findings decide what a principle claims.

## The framework in one screen

Four objectives (the value lens): **Cost**, **Quality**, **Governance** (control/risk and
evidence/audit), **Human-Agent Collaboration**.

Ten principles in two pillars:

| # | Principle | Primary objective | One-line commitment |
|---|---|---|---|
| P1 | Concepts Defined by People | Collaboration | People originate the work as one complete written brief; intent can change, so artifacts carry an override protocol |
| P2 | Architecture | Governance (control) | People choose the system shape (structure, toolsets, staged adoption) before agents run; default to one capable generalist |
| P3 | File-Based Inputs, Evidence and Outputs | Governance (evidence) | Files are the versioned interface both ways: inputs bound work, evidence records it, outputs are captured for audit and reuse |
| P4 | Acceptance Criteria | Quality | "Done" is a deterministic gate defined before the work, checked by something other than the agent, and audited |
| P5 | Skills for People | Collaboration | The scarce skill is human: precise specification, scoping judgement, risk management, shared vocabulary |
| P6 | Token Resources Management | Cost | Treat tokens like cloud spend: budget in dollars not tokens, attribute, right-size the model, amortize artifacts |
| P7 | Human Review Gates | Governance (control) | Autonomy is granted per action; high-stakes actions stop for a human; gates are verified outside the agent's reach |
| P8 | Agent-Friendly Languages | Cost | Least verbose language or format that captures intent; structured for machines, narrative for humans |
| P9 | Loops | Quality | Plan, execute, observe, adapt, with bounded iterations and a defined exit |
| P10 | Retrospectives | Quality | Score outcomes and feed learnings forward, paired with external signal (the weakest-evidenced principle) |

Methods and techniques the framework has measured, by short name (used in the table below):

* **Complete brief up front** (t10, a01): one fully specified prompt beat vague prompting plus 3-5 clarification turns by 51-70%; live, 0% to 92% gate-pass on a moderately specified task.
* **Decision ledger with override protocol** (t01, t18, a06): anchors intent across sessions but can entrench drift; do not add a ledger only for override safety.
* **One generalist versus orchestrator plus specialists** (t14, t22, a02): orchestration cost 54-63% more with no crossover; live, the single agent won cost (-45 to -49%), reliability (100% vs 68-76%) and latency (-32 to -37%). Auditability and role-separated review are its only remaining defence.
* **Codified module over restated requirements** (t09): 25/25 vs 12/25 at about 14 NFRs.
* **Prebuilt index, fresh** (t11, a03): 19-44% cheaper (-52/-53% live), but a stale index failed the freshness check 0/25 while re-retrieval passed 18/25. Version it; rebuild or freshness-check on a schedule.
* **Per-agent requirements slice** (t04): give each agent only its slice, 5-13% cheaper.
* **Stored script versus improvised** (t06): prebuilt wins 30-31%; a self-built one pays back only after several reuses.
* **Deterministic checker** (t07, harness gate design): 25/25 vs 8/25 above about 100 items; below about 40 items reasoning was as reliable and cheaper.
* **Separate validity from graded quality** (a07): a "did it run" gate read 100% while graded quality read 0% in the same run.
* **LLM judge** (a12): prior only, not live evidence; keep a deterministic gate and a person on final sign-off for money decisions.
* **Hardened anti-evasion prompt wording** (t20): caught nothing and cost 37-44% more.
* **Specification checklist for the author** (t21, a09): 100% vs 0% on deceptively simple tasks; null on genuinely ambiguous ones.
* **Configured keyword vocabulary** (t05): 24-68% cheaper.
* **Scoping judgement** (t03): 38-42% cheaper against monorepo noise; reverses in a tiny repo.
* **Model right-sizing** (t12, a04): 2.3-5x cheaper; live, `gpt-5.4-mini` held 100% on hard work at -73%, and the stronger default failed the routine contract 0% vs 100%. Requalify each tier against real tasks.
* **Cache-aware cost** (H16): about 96% of input served from cache; budget and report in `est_cost` dollars, never raw tokens.
* **Backpressure over naive retry** (a10): under 2-3x overload naive retry congestion-collapsed; backpressure served 2.2-3.8x more.
* **Code-enforced versus prompt-enforced gate** (a05): the ">$50 never auto-resolves" invariant held 100% in both arms, including under social engineering; keep the code gate as the backstop, do not credit it for what the prompt already did.
* **Externally verified gate** (harness audit): an agent wrote its solution into the fixture directory and every later run passed pre-solved; a gate the agent can influence is not a control.
* **Ceremony-light language** (t13): Python 36-66% cheaper than Go/Java at identical behavior, model-specific.
* **Structured format** (a08): -5% on a detailed ticket, null on a simple one; standardize on complex, error-prone work.
* **Compact instructions** (t02): pays only at aggressive (about 66%) compression; mild compaction is a dead heat.
* **Reminder versus re-brief** (t08): a short reminder beats a full re-brief only while instructions are still in context.
* **Durable hand-off for recovery** (a11): about 2x cost and slower with no measurable reliability gain; give the loop a finish test and a retry cap instead of machinery you cannot show pays off.
* **Self-review versus fresh-eyes critic** (t15, t17): self-review found as many or more defects at about 8% less cost.
* **Feed-forward lessons** (t23, a07): not supported live (0% defect-free on both arms); earn it per deployment with a graded metric.

## Cross-cutting: what applies to the whole workshop

* **P5 Skills for People (t21, a09).** The largest live lift the framework found came from a
  guided author on deceptively simple tasks (0% to 90%). The workshop's shared brief
  (`USE-CASE.md`), the fixed scenarios and the specification checklist style of every lab README
  are that skill made visible. Consider a 5-minute checkpoint in Lab 1 where learners write the
  brief for a fourth scenario before touching code.
* **P6 and P4 together.** A cheaper run that fails the acceptance contract is not an efficiency
  win. Every cost comparison in Lab 4 is made only among gate-passers.
* **P3 freshness as a governance duty (a03).** Knowledge docs, skills, indexes and session records
  are all durable artifacts; each needs an owner and a rebuild or expiry rule. The labs set
  `last_reviewed` on docs and a TTL on session records for this reason.
* **Negative findings are architectural guidance.** Separate fresh-eyes critics, orchestration for
  presumed efficiency, ledgers added only for override safety, and reflexively hardened gates all
  added cost without proving their benefit in the measured scenarios. Labs 3 and 4 name these
  trade-offs rather than presenting multi-agent and evaluation as free wins.

## Where the framework does not apply, or applies weakly

* **P10 Retrospectives** is the framework's weakest-evidenced principle (a07 not supported live).
  Lab 4 frames evaluation-fed instruction changes as a practice to earn, not a proven technique.
* **Programming-language facet of P8 (t13)** is SWE-only; it applies to the hosted code, not to the
  agents' business behavior.
* **a10 backpressure** ran live from an in-VNet VM at a real 500k TPM quota; the labs teach it as
  a directional operating rule, not a tuned setting.
